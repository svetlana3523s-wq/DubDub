# PROJECT_SUMMARY.md

## 1. Что это за проект

**DubDub** — это Telegram Mini App (веб-приложение внутри Telegram) для совместной озвучки видео.

### Что делает Telegram-бот:
- Принимает команды пользователей (`/start`, `/help`, `/scenes`)
- Помогает админам загружать видео через бота (можно отправить файл или URL)
- Позволяет админам редактировать тайминги реплик в видео (cue timings)
- Отправляет пользователям ссылки на игру через deep links
- Отправляет готовые видео пользователям в личные сообщения

### Что делает Mini App (веб-приложение):
- Страница создания игры: выбор категории (Кино/Мемы/Политика), режима (Импровизация/С заданиями), количества игроков (1 или 2)
- Страница игры (session): показывает видео, позволяет записывать аудио, отслеживает прогресс
- Страница результата: показывает готовое видео, кнопку "Отправить в Telegram", кнопки повторной игры
- Админ-панель: загрузка/редактирование/удаление сцен через веб-интерфейс

### Как они связаны:
- Бот открывает Mini App по ссылке (deep link) — пользователь кликает кнопку в боте, открывается веб-приложение
- Mini App обращается к API серверу (который также содержит логику бота)
- После рендера видео отправляется через Telegram Bot API пользователю в личные сообщения

## 2. Общая архитектура

Проект состоит из **3 основных сервисов**:

### API сервер (`apps/api/`)
- **Технология**: Fastify (веб-фреймворк для Node.js)
- **Порт**: 4000 (локально)
- **Что делает**:
  - REST API для Mini App (создание сессий, загрузка аудио, получение статуса)
  - Telegram Bot (обработка команд, отправка сообщений)
  - Прокси для файлов из S3 (видео не отдаются напрямую, а через API)
  - Очередь задач для рендеринга (BullMQ)
- **Где код**: `apps/api/src/`
  - `index.ts` — запуск сервера
  - `bot.ts` — логика бота
  - `routes/` — API endpoints
  - `lib/` — утилиты (хранилище, очередь, аутентификация)

### Web приложение (`apps/web/`)
- **Технология**: Next.js 14 (React-фреймворк)
- **Порт**: 3000 (локально)
- **Что делает**:
  - Веб-интерфейс Mini App (все страницы, которые видит пользователь)
  - Компоненты для записи аудио, просмотра видео, админ-панели
- **Где код**: `apps/web/src/`
  - `app/` — страницы (routing)
  - `components/` — React-компоненты
  - `lib/` — клиент для API

### Worker (`apps/worker/`)
- **Технология**: BullMQ (фоновая очередь задач)
- **Порт**: нет (фоновый процесс)
- **Что делает**:
  - Берет задачи из очереди Redis
  - Рендерит видео через FFmpeg (склеивает оригинальное видео + записанные аудио)
  - Загружает результат в S3
  - Обновляет статус в базе данных
- **Где код**: `apps/worker/src/`
  - `index.ts` — обработчик задач очереди
  - `render.ts` — логика рендеринга через FFmpeg

### Хранилище данных:
- **PostgreSQL** (база данных) — хранит сцены, сессии, пользователей, записи аудио
- **Redis** (кэш и очередь) — очередь задач рендеринга (BullMQ), состояние бота
- **S3-совместимое хранилище** (MinIO локально, AWS S3 в продакшене) — видео файлы (оригиналы, записи, готовые рендеры)

### Схема базы данных:
- **Scene** — видео-сцена (название, категория, тайминги реплик, ссылка на S3)
- **Session** — игровая сессия (категория, режим, статус, участники)
- **Participant** — участник сессии (Telegram ID, роль, имя)
- **Take** — записанное аудио (ссылка на S3, длительность, роль)
- **Render** — результат рендеринга (статус, ссылка на готовое видео, ошибки)

## 3. Основные фичи (списком)

### ✅ Реализовано:

1. **Telegram Bot**
   - Команды: `/start`, `/help`, `/scenes`, `/stats`
   - Загрузка видео через бота (файл или URL) для админов
   - Редактирование таймингов реплик через бота
   - Отправка готовых видео пользователям

2. **Создание игры**
   - Выбор категории (🎬 Кино/сериалы | 😂 Мемы | 🏛️ Политика)
   - Выбор режима (🎭 Импровизация | 📝 С заданиями)
   - Выбор количества игроков (1 или 2)
   - Случайный выбор сцены из категории

3. **Игровой процесс**
   - Показ видео сцены с таймингами реплик
   - Запись аудио через браузер (MediaRecorder API)
   - Один бесплатный ретейк на роль
   - Автоматическая обрезка аудио до длительности реплики
   - Режим "С заданиями" — случайные задания для озвучки (например, "Озвучь с кавказским акцентом")

4. **Мультиплеер**
   - Подключение по коду (последние 8 символов ID сессии)
   - Оба игрока записывают одновременно (не по очереди)
   - Каждый игрок видит только свою реплику (фрагмент видео)
   - Подтверждение повторной игры (если один игрок хочет повторить, второй подтверждает)

5. **Рендеринг видео**
   - FFmpeg склеивает оригинальное видео + записанные аудио
   - Замена аудио только в нужных диапазонах (по таймингам реплик)
   - Добавление водяных знаков с именами игроков
   - Retry при таймауте FFmpeg (до 3 попыток: 1 исходная + 2 retry с ожиданием 5s, 10s)
   - Таймаут FFmpeg: 1.5 минуты

6. **Результат**
   - Просмотр готового видео
   - Кнопка "Отправить в Telegram" (отправляет видео в личные сообщения)
   - Повтор игры (та же сцена / новая сцена)
   - Отправка в канал уведомлений (если настроено)

7. **Админ-панель**
   - Загрузка видео через веб-интерфейс
   - Редактирование таймингов реплик (визуальный редактор)
   - Создание двух версий видео: оригинал + версия с вырезанным аудио в диапазонах реплик
   - Удаление сцен

8. **Безопасность**
   - Валидация Telegram initData (HMAC SHA-256)
   - Проверка прав админа (по Telegram User ID)
   - Rate limiting (200 запросов в минуту)

### ⚠️ Частично реализовано / Хрупкие места:

1. **Отправка видео в Telegram**
   - Используется URL метод (как для канала) с fallback на Buffer
   - Иногда возникают сетевые ошибки ("socket hang up")
   - Возможны проблемы с большими видео

2. **Выбор сцен**
   - Простой случайный выбор (без сложной логики "не повторять")
   - При создании новой игры может выпасть та же сцена

3. **Кеширование**
   - Next.js кеширование может вызывать проблемы при обновлении фронтенда
   - Используется `window.location.href` для принудительной перезагрузки страницы после replay

## 4. Стек технологий

### Backend:
- **Fastify** — веб-фреймворк для API
- **Telegraf** — библиотека для Telegram Bot API
- **Prisma** — ORM для работы с PostgreSQL
- **BullMQ** — очередь задач (рендеринг) на основе Redis
- **FFmpeg/FFprobe** — обработка видео и аудио (системные утилиты)
- **AWS SDK (S3)** — работа с S3-совместимым хранилищем
- **ioredis** — клиент для Redis

### Frontend:
- **Next.js 14** — React-фреймворк (App Router)
- **React 18** — UI библиотека
- **Tailwind CSS** — стилизация
- **Telegram WebApp SDK** — интеграция с Telegram Mini App
- **VideoPlayer** — кастомный видеоплеер на HTML5 video (заменил Plyr из-за проблем с кешированием)

### База данных:
- **PostgreSQL** — основная база данных
- **Redis** — кэш и очередь задач

### Хранилище:
- **MinIO** — локально (S3-совместимое хранилище)
- **AWS S3** — в продакшене

### Инфраструктура:
- **Docker Compose** — локальная разработка (PostgreSQL, Redis, MinIO)
- **PM2** — процесс-менеджер для продакшена
- **Nginx** — reverse proxy для API и Web

### Внешние API:
- **Telegram Bot API** — отправка сообщений, работа с ботом
- **Telegram WebApp API** — интеграция Mini App с Telegram

## 6. Как проходит типовой сценарий пользователя

### Сценарий 1: Одиночная игра

1. **Пользователь открывает бота в Telegram** → нажимает кнопку "🎭 Начать игру" (или команда `/start`)
2. **Открывается Mini App** → главная страница (`/`)
3. **Пользователь создает игру** (`/create`):
   - Выбирает категорию (например, "Мемы")
   - Выбирает режим (например, "Импровизация")
   - Выбирает количество игроков: "1"
4. **API создает сессию**:
   - Выбирает случайную сцену из категории "Мемы"
   - Создает запись Session в БД
   - Создает запись Participant (пользователь как участник)
   - Устанавливает статус "recording"
5. **Открывается страница игры** (`/s/[sessionId]`):
   - Показывается видео сцены
   - Показывается фрагмент видео для первой роли (с таймингом)
   - Кнопка "Записать"
6. **Пользователь записывает аудио**:
   - Нажимает "Записать"
   - Идет обратный отсчет (3-2-1)
   - Запись через MediaRecorder API (браузер)
   - Можно один раз перезаписать (ретейк)
7. **Аудио отправляется на сервер**:
   - POST `/sessions/:id/takes` с файлом
   - Сервер обрезает аудио до длительности реплики (FFmpeg)
   - Сохраняет в S3
   - Создает запись Take в БД
8. **Повторяется для всех ролей** (если ролей несколько)
9. **Пользователь нажимает "Собрать видео"**:
   - POST `/sessions/:id/finish`
   - Сервер создает задачу в очереди (BullMQ)
   - Создает запись Render в БД (статус "pending")
   - Устанавливает статус сессии "rendering"
10. **Worker обрабатывает задачу**:
    - Берет задачу из очереди Redis
    - Скачивает оригинальное видео и все аудио из S3
    - Запускает FFmpeg для рендеринга
    - Загружает готовое видео в S3
    - Обновляет статус Render на "ready"
    - Обновляет статус Session на "ready"
11. **Открывается страница результата** (`/s/[sessionId]/result`):
    - Frontend опрашивает статус рендеринга (polling)
    - Когда статус "ready", показывается видео
    - Кнопка "Отправить в Telegram"
    - Кнопки "Еще раз" / "Новая сцена"
12. **Пользователь нажимает "Отправить в Telegram"**:
    - POST `/files/renders/:sessionId/send-to-telegram`
    - API отправляет видео через Telegram Bot API
    - Видео приходит в личные сообщения пользователю

### Сценарий 2: Мультиплеер (2 игрока)

1. **Первый игрок создает игру**:
   - Выбирает количество игроков: "2"
   - Статус сессии "lobby"
2. **Отображается код приглашения** (последние 8 символов ID сессии)
3. **Первый игрок отправляет код второму** (через Telegram или вручную)
4. **Второй игрок присоединяется**:
   - Вводит код в боте (команда "👥 Присоединиться к игре") ИЛИ
   - Переходит по ссылке `https://t.me/BOT?startapp=join_CODE`
   - API находит сессию по коду
   - Создается запись Participant (второй игрок)
   - Статус сессии меняется на "recording"
5. **Оба игрока видят страницу игры**:
   - Каждый видит свой фрагмент видео (для своей роли)
   - Оба могут записывать одновременно
6. **Оба игрока записывают аудио** (параллельно)
7. **Последний игрок (кто записал последним) нажимает "Собрать видео"**
8. **Рендеринг и результат** (как в сценарии 1)
9. **Повторная игра**:
   - Один игрок нажимает "Еще раз" / "Новая сцена"
   - API создает запрос на подтверждение (replayRequest)
   - Второму игроку показывается диалог подтверждения
   - Если подтверждает → сессия сбрасывается (удаляются takes, render), выбирается новая сцена, статус "recording"
   - Оба игрока видят новую игру

## 7. Важные моменты и хрупкие места

### ⚠️ Что легко сломать:

1. **FFmpeg фильтры в `render.ts`**
   - Сложная строка `filter_complex` строится вручную
   - Синтаксическая ошибка = рендер падает
   - **Не трогать** без тестирования на реальных данных

2. **Формат cue (тайминги реплик)**
   - В БД хранятся в кадрах (frames), но старые сцены могут быть в секундах
   - `parseCuesFromJson` пытается обработать оба формата
   - При создании новых сцен всегда использовать frames

3. **Deep links для iOS**
   - Inline кнопки `web_app` на iOS открываются как WebView (без Telegram SDK)
   - Используются текстовые ссылки `?startapp=s_sessionId` вместо inline кнопок
   - **Не возвращаться** к inline `web_app` кнопкам

4. **Telegram WebApp SDK инициализация**
   - `initData` нужен для аутентификации
   - Если SDK не загрузился → пользователь не может авторизоваться
   - Есть retry логика, но может не сработать на медленных соединениях

5. **Навигация после replay**
   - Используется `window.location.href` вместо `router.push` (чтобы обойти кеширование Next.js)
   - **Не менять** на `router.push` без понимания последствий

6. **VideoPlayer компонент**
   - Кастомный компонент на HTML5 video (заменяет Plyr из-за проблем с кешированием)
   - Переключение между оригиналом и версией с cuts через смену `src`
   - **Не возвращаться** к Plyr без серьезной причины

7. **Отправка видео в Telegram**
   - Используется URL метод (как для канала) с fallback на Buffer
   - Могут быть сетевые ошибки ("socket hang up")
   - Большие видео могут не отправиться

8. **Multipart upload (загрузка видео админом)**
   - Большие файлы (>500MB) могут таймаутить
   - Nginx `client_max_body_size` должен совпадать с Fastify `bodyLimit`
   - Чтение файла должно происходить внутри `for await (const part of parts)` цикла

### 🔧 Где возможны баги:

1. **Race conditions при параллельной записи** (мультиплеер)
   - Оба игрока могут отправить аудио одновременно
   - Используется `upsert` для предотвращения дубликатов, но теоретически возможны проблемы

2. **Таймауты FFmpeg**
   - Таймаут 1.5 минуты (может быть мало для длинных видео)
   - Есть retry логика (до 3 попыток: 1 исходная + 2 retry), но может не помочь при больших видео

3. **Случайный выбор сцен**
   - Простой `Math.random()`, может выпасть та же сцена несколько раз подряд
   - Нет сложной логики "не повторять"

4. **Polling на фронтенде**
   - Множественные запросы каждые 2-5 секунд
   - Rate limit 200 req/min может быть превышен при активном использовании

5. **Кеширование Next.js**
   - SSR кеш может показывать старые данные
   - Используется `generateBuildId` с timestamp, но не всегда помогает

### 🚨 Что написано костыльно (если видно):

1. **Принудительная перезагрузка страницы** (`window.location.href`) после replay
   - Костыль для обхода кеширования Next.js
   - Не идеально с точки зрения UX, но работает

2. **Fallback на Buffer** при отправке видео в Telegram
   - URL метод не всегда работает, используется fallback
   - Дважды скачивается видео (один раз для проверки URL метода, второй для Buffer)

3. **Поиск сессии по коду** (последние 8 символов)
   - Загружаются последние 100 сессий, затем фильтрация
   - Не оптимально для большого количества сессий

4. **Простой случайный выбор сцен**
   - Нет сложной логики отслеживания "какие сцены уже игрались"
   - Может повторяться

## 8. Какие части проекта лучше НЕ переписывать без причины

### Критичные компоненты (трогать только с крайней осторожностью):

1. **`apps/worker/src/render.ts`** — логика рендеринга через FFmpeg
   - Очень сложная логика сборки фильтров
   - Любое изменение может сломать рендеринг
   - Тестировать на реальных данных перед деплоем

2. **`apps/api/src/lib/telegram-auth.ts`** — валидация Telegram initData
   - Безопасность: любая ошибка = уязвимость
   - Следует официальной документации Telegram
   - Не менять без понимания HMAC SHA-256

3. **`apps/api/src/routes/sessions.ts`** — логика создания/присоединения/завершения сессий
   - Много бизнес-логики
   - Связано с базой данных и очередью
   - Изменения могут сломать игровой процесс

4. **`apps/web/src/components/VideoPlayer.tsx`** — видеоплеер
   - Заменил Plyr из-за проблем с кешированием
   - Работает стабильно
   - Не возвращаться к Plyr без серьезной причины

5. **`apps/api/src/bot.ts`** — логика Telegram бота
   - Много команд и обработчиков
   - Связано с базой данных и состоянием
   - Изменения могут сломать пользовательский опыт

### Компоненты, которые можно улучшить (но осторожно):

1. **Выбор сцен** — можно добавить логику "не повторять"
2. **Отправка видео в Telegram** — можно улучшить обработку ошибок
3. **Polling** — можно заменить на WebSocket (но это большая переработка)
4. **Навигация** — можно улучшить переходы без полной перезагрузки (но нужно решить проблему кеширования)
