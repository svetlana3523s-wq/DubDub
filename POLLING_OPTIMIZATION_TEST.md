# Чеклист тестирования оптимизации polling и rate limit

## Что изменили

1. **Polling с backoff** — заменен фиксированный интервал 3s на backoff (3s, 3s, 5s, 8s, 13s, потом 15s макс)
2. **Остановка polling** — автоматическая остановка при финальных статусах (sent, failed, too_large)
3. **Таймаут 180 секунд** — после таймаута показывается ошибка
4. **Исключение из rate limit** — GET /renders/:sessionId и GET /files/renders/:sessionId/send-status исключены из глобального rate limit

## Измененные файлы

1. `apps/api/src/index.ts` — добавлена skip функция для rate limit
2. `apps/web/src/app/s/[sessionId]/result/page.tsx` — изменен polling с setInterval на setTimeout с backoff
3. `CURRENT_STATE.md` — обновлена документация

## Чеклист тестирования

### Тест 1: 2 пользователя одновременно

**Сценарий:**
- 2 пользователя в мультиплеерной игре
- Оба завершают игру, дождаться рендера
- Оба нажимают "Сохранить в Telegram" практически одновременно (в пределах 5-10 секунд)

**Ожидаемое поведение:**
- [ ] Оба видео отправляются без ошибок 429/rate limit
- [ ] В логах API нет ошибок rate limit для endpoints `/renders/:sessionId` и `/files/renders/:sessionId/send-status`
- [ ] В Network tab видно, что polling происходит с backoff интервалами (3s → 3s → 5s → 8s → 13s → 15s)
- [ ] Polling останавливается когда статус становится "sent", "failed" или "too_large"
- [ ] Кнопки показывают правильные состояния: "Отправляем..." → "✅ Отправлено в чат!"

**Проверка:**
- Открыть Network tab в DevTools для обоих пользователей
- Проверить, что запросы к `/renders/:sessionId` и `/files/renders/:sessionId/send-status` не возвращают 429
- Проверить интервалы между запросами (должны увеличиваться)
- Проверить логи API сервера (не должно быть ошибок rate limit)

### Тест 2: Остановка polling при финальных статусах

**Сценарий:**
- Завершить игру, дождаться рендера
- Нажать "Сохранить в Telegram"

**Ожидаемое поведение:**
- [ ] После успешной отправки (статус "sent") polling останавливается
- [ ] Кнопка меняется на "✅ Отправлено в чат!"
- [ ] В Network tab больше нет запросов к `/files/renders/:sessionId/send-status`
- [ ] После ошибки (статус "failed" или "too_large") polling останавливается
- [ ] Показывается ошибка пользователю
- [ ] В Network tab больше нет запросов к `/files/renders/:sessionId/send-status`

**Проверка:**
- Открыть Network tab в DevTools
- После отправки проверить, что запросы прекратились
- Проверить UI — кнопка должна показывать финальное состояние

### Тест 3: Таймаут 180 секунд

**Сценарий:**
- Завершить игру, дождаться рендера
- Нажать "Сохранить в Telegram"
- Отправить видео в очередь, но симулировать долгую отправку (или дождаться таймаута)

**Ожидаемое поведение:**
- [ ] После 180 секунд polling останавливается
- [ ] Показывается ошибка "Отправка занимает слишком много времени. Попробуйте позже."
- [ ] Кнопка становится доступной для повторной отправки
- [ ] В Network tab больше нет запросов к `/files/renders/:sessionId/send-status`

**Проверка:**
- Открыть Network tab в DevTools
- Подождать 180 секунд (или изменить MAX_POLL_DURATION для теста)
- Проверить, что показывается ошибка
- Проверить, что polling остановился

### Тест 4: Backoff интервалы

**Сценарий:**
- Завершить игру, дождаться рендера
- Нажать "Сохранить в Telegram"
- Наблюдать за polling в Network tab

**Ожидаемое поведение:**
- [ ] Первый запрос через 3 секунды
- [ ] Второй запрос через 3 секунды (всего 6 секунд от начала)
- [ ] Третий запрос через 5 секунд (всего 11 секунд от начала)
- [ ] Четвертый запрос через 8 секунд (всего 19 секунд от начала)
- [ ] Пятый запрос через 13 секунд (всего 32 секунды от начала)
- [ ] Дальше запросы каждые 15 секунд (максимальный интервал)

**Проверка:**
- Открыть Network tab в DevTools
- Зафиксировать время первого запроса
- Проверить интервалы между запросами
- Интервалы должны соответствовать backoff массиву: [3s, 3s, 5s, 8s, 13s, 15s, ...]

### Тест 5: Rate limit исключение

**Сценарий:**
- 2 пользователя в мультиплеерной игре
- Оба завершают игру, дождаться рендера
- Оба нажимают "Сохранить в Telegram" одновременно
- Оба активно используют polling (рендеринг + отправка)

**Ожидаемое поведение:**
- [ ] НЕТ ошибок 429 (Too Many Requests) для GET /renders/:sessionId
- [ ] НЕТ ошибок 429 (Too Many Requests) для GET /files/renders/:sessionId/send-status
- [ ] Другие endpoints (например, POST /files/renders/:sessionId/send-to-telegram) могут иметь rate limit (это нормально)

**Проверка:**
- Открыть Network tab в DevTools для обоих пользователей
- Проверить все запросы — не должно быть 429 для status endpoints
- Проверить логи API сервера — не должно быть rate limit ошибок для status endpoints
- Проверить, что глобальный rate limit (200 req/min) все еще работает для других endpoints

## Критерии успеха

1. ✅ Нет ошибок 429/rate limit при 2 пользователях одновременно
2. ✅ Polling останавливается при финальных статусах
3. ✅ Таймаут работает (180 секунд)
4. ✅ Backoff интервалы применяются правильно
5. ✅ Status endpoints исключены из rate limit
